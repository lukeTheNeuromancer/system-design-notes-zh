# 第 10 章：设计通知系统 (Design a Notification System)

## 简介
**通知系统 (notification system)** 是现代应用不可或缺的部分，提供产品通知、活动、优惠、告警等及时更新。通知可通过以下渠道发送：
1. **推送通知**（移动端或桌面端）、
2. **短信**、
3. **邮件**。

本章聚焦于设计可扩展的系统，使其每天能够发送数百万条通知。

---

## 步骤 1：理解问题
### 需求
- **通知类型：** 推送通知、短信和邮件。
- **投递：** 软实时系统，延迟尽量小。
- **平台：** iOS、Android 和桌面端。
- **触发方式：** 通知可由客户端应用触发，或在服务端定时触发。
- **规模：**
  - **推送通知：** 1000 万条/天、
  - **短信：** 100 万条/天、
  - **邮件：** 500 万条/天。
- **退订支持：** 用户可关闭特定类型的通知。

---

## 步骤 2：高层设计

### 组件

1. **通知类型：**
   - **iOS 推送通知：** 使用 **Apple Push Notification Service (APNS)**。
   - **Android 推送通知：** 使用 **Firebase Cloud Messaging (FCM)**。
   - **短信：** 使用 Twilio 或 Nexmo 等第三方服务。
   - **邮件：** 使用 SendGrid 或 Mailchimp 等商业邮件服务。

2. **联系信息收集：**
   <div style="margin-left:3rem">
      <img src="./images/contact-info-gathering.png" alt="联系信息收集" width="500">
   </div>

   - 在应用安装或注册时收集设备令牌、手机号或邮箱地址。
   - 将联系信息存入数据库：
     - **设备令牌表：** 用于推送通知。
     - **用户表：** 用于邮箱和手机号。


3. **通知发送流程：**

   <div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="高层设计" width="500">
   </div>

   - **触发服务 (Trigger Services)：**
      - 生成事件以发起通知（例如账单提醒、物流更新）。
      - 一个服务可以是微服务、定时任务 (cron job)，或触发通知发送事件的分布式系统。
   - **通知服务器 (Notification Server)：**
      - 为服务提供发送通知的 API。
      - 做基础校验，验证邮箱、手机号。
      - 查询数据库或缓存，获取渲染通知所需的数据。
   - **第三方服务：** 将通知投递给用户。



### 初始设计的挑战
- **单点故障 (SPOF)：** 一台通知服务器故障会拖垮整个系统。
- **扩展性问题：** 难以对数据库、缓存和处理组件独立扩展。
- **性能瓶颈：** 发送通知的资源需求很高。

### 改进后的设计

   <div style="margin-left:3rem">
      <img src="./images/improved-design.png" alt="改进后的设计" width="500">
   </div>

- 将数据库和缓存移出通知服务器。
- 引入**水平扩展**，部署多台通知服务器。
- 使用**消息队列**解耦系统组件。
   -  当需要发送大量通知时，消息队列充当缓冲。
- 增加工作进程，从消息队列拉取通知事件并发送给对应的第三方服务。



---

## 步骤 3：设计深挖

### 可靠性
1. **防止数据丢失：**
   <div style="margin-left:3rem">
   <img src="./images/data-loss.png" alt="数据丢失" width="400">
   </div>

   - 将通知数据持久化到数据库，并实现重试机制。
   - 加入通知日志数据库用于数据持久化。


2. **去重：**
   - 检查事件 ID，避免发送重复通知。
   - 通知事件首次到达时，通过检查事件 ID 判断是否已见过。若已见过则丢弃，否则发送通知。


### 其他组件
   <div style="margin-left:3rem">
   <img src="./images/events-tracking.png" alt="事件跟踪" width="400">
   </div>

1. **通知模板：** 预先格式化好的模板，保证通知一致、高效。
2. **通知设置：**
   - 用户可按渠道（推送、短信或邮件）选择订阅或退订。
   - 存储在专用的通知设置表中。
3. **限流：** 限制发给用户的通知频率。
4. **重试机制：** 第三方服务失败时重试发送通知。
5. **队列监控：** 跟踪队列中的通知，以动态扩展工作进程。
6. **事件跟踪：** 收集打开率、点击率、参与度等指标。


### 安全
- 使用 **AppKey** 和 **AppSecret** 对推送通知的 API 做鉴权和安全保护。

### 通知流程

   <div style="margin-left:3rem">
   <img src="./images/updated-design.png" alt="更新后的设计" width="500">
   </div>

1. 触发服务调用 API 发送通知。
2. 通知服务器校验请求，并从缓存或数据库获取元数据。
3. 通知事件被发送到消息队列。
4. 工作进程处理事件并与第三方服务交互。
5. 第三方服务将通知投递给用户。


---

## 关键优化
1. **水平扩展：** 增加通知服务器以分担负载。
2. **消息队列：** 解耦处理流程，应对高并发。
3. **缓存：** 缓存高频访问数据以降低延迟。
4. **分布式投递：** 按地域优化消息投递以获得更好性能。
