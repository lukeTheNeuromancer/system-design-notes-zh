# 第 11 章：设计动态消息流系统 (Design a News Feed System)

## 简介
**动态消息流系统 (news feed system)** 展示持续更新的帖子列表（状态更新、照片、视频和链接），内容来自用户的社交关系。例子包括 Facebook 的动态消息、Instagram 的信息流和 Twitter 的时间线。本章探讨可扩展的动态消息流系统的设计。

---

## 步骤 1：理解问题

### 需求
1. **平台：** 系统同时支持 Web 和移动应用。
2. **功能：**
   - 用户可以发布帖子。
   - 用户可以在动态消息流中查看好友的帖子。
3. **排序：** 为简单起见，消息流按**逆时间顺序**排序。
4. **规模：**
   - 用户最多可有 5,000 个好友。
   - 1000 万日活跃用户 (DAU)。
   - 消息流可包含文本、图片和视频。

---

## 步骤 2：高层设计

### 概览
设计包含两个主要流程：
1. **消息流发布：** 用户发布帖子，写入数据库并扩散到好友的消息流。
2. **动态消息流构建：** 用户按逆时间顺序聚合好友帖子，获取自己的动态消息流。

---

### 动态消息流 API
1. **消息流发布 API：**
   - **端点：** `POST /v1/me/feed`
   - **参数：** `content`（帖子文本）和 `auth_token`（鉴权）。

2. **动态消息流获取 API：**
   - **端点：** `GET /v1/me/feed`
   - **参数：** `auth_token`（鉴权）。

1. **用户交互：** 用户通过消息流发布 API 发布帖子。
2. **负载均衡器：** 将流量分发到 Web 服务器。
3. **Web 服务器：** 做请求鉴权并转发到各服务。
4. **帖子服务：** 将帖子存入数据库和缓存。
5. **扩散服务：** 将帖子扩散到好友缓存中的动态消息流。
6. **通知服务：** 向好友发送通知。

1. **用户交互：** 用户通过获取 API 请求自己的动态消息流。
2. **负载均衡器：** 将流量分发到 Web 服务器。
3. **Web 服务器：** 将请求转发到动态消息流服务。
4. **动态消息流服务：** 从动态消息流缓存获取帖子 ID，再从数据库或缓存获取完整的帖子详情。

## 步骤 3：设计深挖

### 消息流发布深挖
1. **Web 服务器：**
   - 使用 `auth_token` 做用户鉴权。
   - 执行限流以防垃圾信息。

2. **扩散服务：**
   - **写扩散 (Fanout on Write)：** 在写入时将帖子推送到好友的消息流。
     - **优点：** 实时更新，消息流读取快。
     - **缺点：** 对好友众多的用户资源消耗大。
   - **读扩散 (Fanout on Read)：** 在读取时拉取帖子。
     - **优点：** 对不活跃用户高效。
     - **缺点：** 消息流读取较慢。
   - **混合方案：** 对大多数用户用推模式，对高连接数用户（如明星）用拉模式。

        <img src="./images/feed-publishing-deep-dive.png" alt="消息流发布深挖" width="500">

    **扩散服务**的工作流程如下：

    1. **获取好友 ID：** 从图数据库获取好友列表。
    2. **从缓存过滤好友：** 访问缓存中的用户设置，排除特定好友（例如屏蔽的好友或选择性分享偏好）。
    3. **发送到消息队列：** 将过滤后的好友列表连同新帖子 ID 发送到消息队列处理。
    4. **扩散工作进程：** 工作进程从消息队列取数据并更新动态消息流缓存。缓存存储 `<post_id, user_id>` 映射而非完整的用户和帖子对象，以节省内存。
    5. **存入动态消息流缓存：** 将新帖子 ID 追加到好友的动态消息流缓存。可配置的上限保证只存最近的帖子，因为大多数用户只关注最新内容，这样缓存内存占用可控。

## 动态消息流获取深挖

### 缓存架构
缓存分为五层：
1. **动态消息流缓存：** 存储帖子 ID，便于快速读取。
2. **内容缓存：** 存储帖子详情（热门帖子放在热缓存）。
3. **社交图谱缓存：** 存储用户关系数据。
4. **行为缓存：** 跟踪用户行为（点赞、回复、分享）。
5. **计数器缓存：** 维护点赞、回复、关注者等计数。

## 关键优化

### 扩展性
1. **数据库扩展：**
   - 水平扩展和分片。
   - 对高流量查询使用读副本。
2. **无状态 Web 层：** Web 服务器保持无状态以支持水平扩展。

### 缓存
1. 将高频访问数据存在内存中。
2. 用缓存层降低延迟和数据库负载。

### 可靠性
1. **一致性哈希：** 将请求均匀分布到各服务器。
2. **消息队列：** 解耦系统组件并缓冲流量。

### 监控
1. 跟踪 QPS（每秒查询数）、延迟等关键指标。
2. 监控缓存命中率并相应调整配置。
